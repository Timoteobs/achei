A separação é modular no código. O banco permanece em um único schema físico, usando o schema padrão do SQL Server.

Decisões arquiteturais registradas

  • O projeto segue a divisão Presentation, Application, Domain, Data e Crosscutting.
  • Contratos de segurança ficam na Application; implementações criptográficas ficam em Crosscutting.
  • A Presentation é a raiz de composição e registra banco, criptografia, hash e JWT.
  • Relacionamentos do EF usam DeleteBehavior.NoAction para evitar exclusões em cascata e múltiplos caminhos no SQL Server.
  • ItemTag e Favorite herdam BaseEntity, mas o mapping ignora Id e mantém as chaves primárias compostas do modelo.
  • Segredos não são versionados em appsettings.json; desenvolvimento usa User Secrets e produção deve usar um cofre ou variáveis injetadas.

Onde estamos

A fundação técnica está pronta: domínio, validação, segurança, contexto e mappings compilam e foram validados. O projeto ainda não possui casos de uso, repositórios específicos, endpoints funcionais do produto, migration inicial nem banco criado.

Ponto de decisão: a entidade User ainda não possui PasswordHash. Portanto, a API sabe gerar e validar JWT, mas ainda não existe um processo que autentique uma pessoa e autorize a emissão do token.

Próximos passos recomendados

  1. Finalizar as configurações locais

    Confirmar Jwt:Key e ConnectionStrings:DefaultConnection nos User Secrets.

  2. Definir o método de autenticação

    Escolher entre e-mail/senha, provedor externo ou acesso sem senha. Para e-mail/senha, adicionar password_hash ao modelo, entidade e mapping.

  3. Criar a migration inicial

    Gerar a migration, revisar o SQL produzido — especialmente chaves compostas, índices e FKs — e só então aplicar no banco.

    dotnet ef migrations add InitialCreate --project Data --startup-project Presentation
dotnet ef database update --project Data --startup-project Presentation

  4. Implementar acesso a dados e casos de uso

    Criar repositórios necessários e começar pelos fluxos de cadastro, autenticação, criação de espaço e gestão de membros.

  5. Expor endpoints da API

    Adicionar controllers e modelos de entrada/saída. Usar [Authorize] nas rotas protegidas e validar acesso por membro e papel no espaço.

  6. Completar o ciclo de autenticação

    Depois do login básico, avaliar refresh token, revogação, recuperação de senha e confirmação de e-mail.

  7. Adicionar testes automatizados

    Cobrir regras do domínio, mappings, autenticação e autorização; incluir testes de integração com SQL Server.

  8. Limpeza e operação

    Remover classes placeholder restantes, decidir o papel de Crosscutting.IOC, configurar logs, health checks e pipeline de CI.
